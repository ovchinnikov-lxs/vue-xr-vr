# 2026-11-22

## Quest system keyboard (8ea5132)

### Done
- In Quest Browser a focused XrTextField opened both XrKeyboard and the
  system keyboard. XrKeyboard without v-model now hides itself in a session
  with a system keyboard; new prop `preferSystemKeyboard` (default true) and
  `useXr().systemKeyboard`. The playground drops the keyboard window and the
  language tabs there (#54).
- The caret now follows text typed on the system keyboard instead of
  staying where it was.

### How
- Detection: `XRSession.isSystemKeyboardSupported` (a Chromium attribute,
  true only in Quest Browser), read reactively from the session in the
  controller. Hiding is `display: 'none'` on the keyboard root, so its
  state (layout, shift) survives; voice input stops when it hides.
- A keyboard with v-model never hides: it edits a string with no DOM input
  behind it, so the system keyboard cannot reach it.
- Caret: uikit reads the hidden input's selection only on its input / key /
  focus events. XrTextField re-reads it every frame while focused (through
  the public `input.focus()` with no range), which covers any event order.
- Rejected: suppressing the system keyboard with `inputmode="none"` and
  keeping ours. Aleksandr wants the native one where it exists.

### Learned
- The bug pattern (caret left, letters to its right, text not reversed)
  means the DOM selection is right and only uikit's copy is stale.
- E2E fakes the Quest by wrapping `navigator.xr.requestSession` and defining
  `isSystemKeyboardSupported` on the returned session; the caret test fails
  without the per-frame sync.
- The exact Quest event order is still a guess; the per-frame read does not
  depend on it.
